# Dependency review and lockfile process

**Owner:** repository administrator
**Applies to:** Python packages and frontend (pnpm) packages
**Requirements:** R16.3, R16.4, R16.7, R16.8, R18.6
**Last updated:** September 19, 2026

This document is the explicit review process required by Requirement 16.7
("pin or lock production dependency versions and review unusual or newly
introduced packages before installation"). It also records the rollback path for
every change it governs.

---

## 1. Files of record

| Concern | File | Role |
| --- | --- | --- |
| Python direct deps | `requirements.in` | Human-edited source of truth. Exact `==` pins only. |
| Python full graph | `requirements.lock` | Generated by `pip-compile --generate-hashes`. Includes transitive deps and per-artifact hashes. **Install from this.** |
| Python legacy runtime | `requirements.txt` | Kept because Heroku and the existing dashboard still read it. Must stay a subset consistent with `requirements.in`. |
| Frontend deps | `web/package.json` | Exact versions (`save-exact=true`). |
| Frontend full graph | `web/pnpm-lock.yaml` | Generated by pnpm. **Install from this.** |
| Secret scanner | `.pre-commit-config.yaml`, `.gitleaks.toml` | gitleaks pinned to `v8.21.2`. |
| CI gate | `.github/workflows/secret-and-dependency-hygiene.yml` | Runs the scan, both audits, and both lockfile-integrity checks. |

Rule: a lockfile and its input file change in the **same commit**. A pull
request that edits `requirements.in` without `requirements.lock` (or
`web/package.json` without `web/pnpm-lock.yaml`) is failed by CI, not by a
reviewer's memory.

### Why two Python files

`requirements.txt` predates this spec and is still what the Heroku deployment
installs. The spec's execution rules require the existing deployment to keep
working, so it stays. `requirements.in` / `requirements.lock` are the
reproducible pair that new work uses. When they diverge, `requirements.in` wins
and `requirements.txt` gets corrected.

## 2. Pinning rules

1. **No open ranges anywhere.** No `>=`, no `~=`, no `^`, no `*`, no
   `latest`. This applies to application dependencies, dev tooling, CI tool
   installs, GitHub Actions (pinned by commit SHA with a version comment), and
   container/runtime versions.
2. **Install from the lockfile, not the input file.**
   - Python: `pip install --require-hashes -r requirements.lock`
   - Frontend: `pnpm install --frozen-lockfile`
3. **Hashes are required for Python.** `--generate-hashes` plus
   `--require-hashes` means a tampered or substituted artifact fails the
   install rather than executing.
4. **One package manager per ecosystem.** pnpm for the frontend. A stray
   `package-lock.json` or `yarn.lock` is a defect.
5. **No install-time script execution by default.** `web/.npmrc` sets
   `ignore-scripts=true`. Allowlist a specific package during review if it
   genuinely needs a build step.

## 3. Review checklist for a new or upgraded package

Complete this before running the install command, and paste the answers into
the pull request. The point is that an unfamiliar package gets thirty seconds of
thought before it gets code execution on a developer machine.

**Identity**

- [ ] Name spelled exactly as the upstream project spells it. Check for
      typosquats: transposed letters, hyphen/underscore swaps, added
      `-js`/`py-` affixes, homoglyphs.
- [ ] Repository and homepage links resolve to the real project, and the
      package page links to that repository.
- [ ] Not a brand-new package with a suspiciously familiar name.

**Health**

- [ ] Actively maintained: a release or meaningful commit within roughly the
      last 12 months, or an explicit "stable and complete" statement.
- [ ] License is compatible with this project's use.
- [ ] Download/usage volume is plausible for what the package claims to be.

**Risk surface**

- [ ] Transitive dependency count is proportionate. A one-line utility pulling
      forty packages is a reason to reconsider or vendor the behavior.
- [ ] No install-time or postinstall scripts. If present, read them and record
      what they do.
- [ ] No unexpected network, filesystem, or credential access for the stated
      purpose.
- [ ] It does not read environment variables or credential files that this
      project treats as secret. Cross-check against `.env.example` key
      **names** (never values).

**Necessity**

- [ ] The standard library or an already-present dependency cannot do this
      reasonably.
- [ ] The version is the current stable release, or the pin to an older
      version has a recorded reason.

**Escalation.** Any of the following requires owner approval before merge:
a package with fewer than ~1000 weekly downloads; any postinstall script; any
package that handles credentials, cryptography, authentication, or
deserialization; any transitive dependency added by an AWS/agent SDK that
brings its own network client.

## 4. Procedures

### 4.1 Add or upgrade a Python dependency

```bash
# 1. Install the pinned tooling (exact versions, matching CI).
python -m pip install pip-tools==7.4.1 pip-audit==2.7.3

# 2. Edit requirements.in. Exact pin only, e.g. fastapi==0.115.6

# 3. Re-lock. Regenerates the full hashed graph.
pip-compile --generate-hashes --output-file requirements.lock requirements.in

# 4. Audit the resulting locked set.
pip-audit --strict --require-hashes --requirement requirements.lock

# 5. Recreate the local environment from the lock and run the tests.
pip install --require-hashes -r requirements.lock
python -m pytest

# 6. Commit requirements.in and requirements.lock together.
```

If the package is also needed by the live Heroku dashboard, add the same exact
pin to `requirements.txt` in the same commit.

### 4.2 Add or upgrade a frontend dependency

```bash
cd web

# save-exact=true writes an exact version, not a range.
pnpm add <package>@<exact-version>

pnpm audit --audit-level moderate
pnpm install --frozen-lockfile   # confirms the lockfile is self-consistent

# Commit web/package.json and web/pnpm-lock.yaml together.
```

### 4.3 Upgrade the secret scanner or CI tooling

gitleaks is pinned in two places and they must agree:

- `.pre-commit-config.yaml` → `rev: v8.21.2`
- `.github/workflows/secret-and-dependency-hygiene.yml` → the
  `gitleaks/gitleaks-action` step, pinned by commit SHA

Procedure: bump both, run `pre-commit run --all-files`, and confirm the scan
still reports **zero** findings and still blocks on a deliberately planted
dummy credential (see §5.2). GitHub Actions are pinned by commit SHA with a
trailing version comment; update the SHA and the comment together.

## 5. Enforcement

### 5.1 Automated gates

| Gate | Where | Failure mode |
| --- | --- | --- |
| Secret scan (staged diff) | pre-commit, gitleaks v8.21.2, `--redact` | Commit blocked; path reported, value redacted |
| Secret scan (full history) | CI `secret-scan` job, `fetch-depth: 0` | Build blocked |
| Python lockfile integrity | CI `python-hygiene`, re-runs `pip-compile` and diffs | Build blocked on drift |
| Python vulnerability audit | CI `python-hygiene`, `pip-audit --strict --require-hashes` | Build blocked |
| Frontend lockfile integrity | CI `frontend-hygiene`, `pnpm install --frozen-lockfile` | Build blocked on drift |
| Frontend vulnerability audit | CI `frontend-hygiene`, `pnpm audit --audit-level moderate` | Build blocked at moderate+ |

The CI workflow performs static checks only. It never calls Tavily, Bedrock,
AgentCore, or a live RunSignup endpoint, and it never reads a real credential.

### 5.2 Verifying the scanner actually blocks

Do this on a scratch branch, and never with a real key:

```bash
git checkout -b scratch/verify-gitleaks
printf 'TAVILY_API_KEY=tvly-dummyvalueforverification\n' > scratch_probe.txt
git add scratch_probe.txt
git commit -m "probe"     # must FAIL, reporting the path with the value redacted
git restore --staged scratch_probe.txt && rm scratch_probe.txt
git checkout - && git branch -D scratch/verify-gitleaks
```

Expected: the commit is rejected, the output names `scratch_probe.txt`, and the
secret is shown redacted. Note that `.gitleaks.toml` allowlists placeholder
words such as `dummy` and `example`, so a probe token containing those words may
be intentionally ignored — use a placeholder-free random token shape when
testing the block behavior, and never a live credential.

## 6. Rollback paths

Every change this document governs is reversible by reverting files. No
external state is mutated.

| Change | Rollback |
| --- | --- |
| Python dependency change | `git revert` the commit (or `git checkout <prev-sha> -- requirements.in requirements.lock requirements.txt`), then `pip install --require-hashes -r requirements.lock` to restore the environment. |
| Frontend dependency change | `git checkout <prev-sha> -- web/package.json web/pnpm-lock.yaml`, then `pnpm install --frozen-lockfile`. |
| Frontend scaffold as a whole | Delete `web/` and the `frontend-hygiene` job. Nothing else imports it; Python jobs are unaffected. |
| Lockfile pair unusable / cannot reproduce | Fall back to `pip install -r requirements.txt`, which is the pre-existing Heroku path and still works. Record the reason and reopen the lock task. |
| CI workflow regression | `git revert` the workflow commit, or disable the specific job from the Actions tab. Pre-commit secret scanning keeps working independently. |
| Pre-commit hook blocking legitimate work | Add a narrowly scoped path or regex entry to the `[allowlist]` in `.gitleaks.toml` with a comment explaining why. Do **not** use `--no-verify`, and do not disable the hook. |
| Scanner upgrade causes false positives | Restore the previous `rev` in `.pre-commit-config.yaml` and the previous action SHA in the workflow. Both are single-line reverts. |

## 7. If a real credential is ever committed

Requirement 16.5: **revoke or rotate first.** History rewriting alone is not
sufficient remediation, because the value may already have been fetched.

1. Rotate the credential in the issuing system immediately.
2. Update the value in its secret store (local environment variable for
   development, SSM SecureString for deployed environments) via the interface
   in `src/xc_platform/security/config.py`. Reference keys by **name** only.
3. Only then consider history cleanup.
4. Record the incident with timestamp, affected path, and rotation
   confirmation. Never record the value.

---

## 8. Review cadence

- **Every pull request that touches a dependency file:** §3 checklist.
- **Monthly:** run both audits on `main`; triage new advisories.
- **Before each release or deployment change:** confirm lockfile integrity
  passes and the deployed runtime version still matches `runtime.txt`.
